# Udemy День 5 — Git 15–18

## Видео 15. Push ветки на GitHub

- `git push origin feature1` — отправляет локальную ветку feature1 на удалённый репозиторий GitHub.
- `git switch main` (после коммита в feature1) — переключает на main. Файлы в папке возвращаются к состоянию ветки main, а изменения из feature1 остаются в этой ветке.
- `git switch feature1` — переключает обратно на feature1, и файлы возвращаются к состоянию этой ветки.

## Видео 16. Как устроены ветки

- Ветка — это указатель на последний коммит определённой линии разработки.
- `HEAD` — это указатель, который показывает, на какой ветке или коммите я сейчас нахожусь.
- `git log` — `HEAD -> main` означает, что сейчас я нахожусь на ветке main.
- `git log --graph` — показывает историю коммитов в виде графа, включая связи между ветками и объединения.
- Родитель (parent) коммита — это предыдущий коммит, на основе которого был создан текущий коммит.

## Видео 17. Merge

- `git merge feature1` — объединяет изменения из feature1 с текущей веткой.
- На какой ветке нужно стоять перед merge: на той, в которую я хочу влить изменения, например на main.
- `git pull origin main` — получает последние изменения из удалённой ветки main и объединяет их с локальной веткой main.
- Зачем делать pull перед merge: чтобы получить последние изменения от других разработчиков и избежать конфликтов и проблем при отправке кода.
- `git push origin main` — отправляет локальную ветку main на GitHub.

## Видео 18. Rebase

- `git branch feature2` — создаёт новую ветку feature2, но не переключает на неё.
- Чем отличается от `git switch -c feature2`: первая команда только создаёт ветку, а вторая создаёт ветку и сразу переключает на неё.
- `git add .` — добавляет все новые и изменённые файлы в текущей директории и её поддиректориях в область подготовки (Staging Area).
- `git switch -` — переключает на предыдущую ветку.
- `git rebase feature3` — переносит коммиты текущей ветки поверх ветки feature3, создавая новые коммиты с новыми хешами.

### Merge или Rebase: что видно на графе

- **Merge:** сохраняет историю обеих веток и может создавать отдельный merge-коммит. История показывает, что ветки были объединены.
- **Rebase:** переносит коммиты на новую основу, создавая более линейную и чистую историю без дополнительного merge-коммита.

### Когда что выбирать

- **Merge:** когда нужно сохранить настоящую историю разработки и объединить работу нескольких разработчиков.
- **Rebase:** когда нужно сделать историю коммитов более линейной и удобной для чтения. Не рекомендуется переписывать общую историю веток, которыми пользуются другие разработчики.

## Что сделал руками

- Создал ветку feature1 с помощью `git switch -c feature1`.
- Сделал изменения в файлах и создал коммит.
- Переключился на main с помощью `git switch main`.
- Объединил feature1 с main с помощью `git merge feature1`.
- Отправил изменения на GitHub с помощью `git push origin main`.

### Что увидел в `git log --graph`

Увидел историю коммитов в виде графа, связи между ветками, их родительские коммиты и результат объединения через merge.
