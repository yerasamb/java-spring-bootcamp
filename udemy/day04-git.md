# Udemy — День 4. Git 11–14

## Git 11 — Origin и теги (Tags)

**1. `git remote -v`**

Показывает список удалённых репозиториев и их адреса. `origin` — стандартное имя удалённого репозитория. `fetch` показывает адрес для получения изменений, а `push` — адрес для отправки изменений.

**2. `git tag`**

Показывает список всех тегов в проекте. Тег — это метка, которая указывает на определённый коммит. Обычно теги используют для обозначения версий программы, например v1.0 или v2.0.

**3. `git tag -a v1.0 -m "first release"`**

Создаёт аннотированный тег (Annotated Tag) для текущего коммита.

- `-a` — создаёт аннотированный тег.
- `v1.0` — название тега.
- `-m` — добавляет сообщение к тегу.

Аннотированный тег хранит имя автора, дату создания и сообщение.

**4. `git show v1.0`**

Показывает подробную информацию о теге и коммите, на который он указывает. Можно увидеть автора, дату, сообщение и изменения коммита.

**5. `git push origin v1.0`**

Отправляет конкретный тег v1.0 на GitHub. Команда `git push origin main` отправляет ветку main, но не отправляет все теги автоматически.

## Git 12 — Работа с чужим репозиторием

**1. `git clone URL`**

Клонирует удалённый репозиторий на локальный компьютер. Создаётся копия проекта со всеми файлами и историей коммитов.

**2. `git log --pretty=oneline`**

Показывает историю коммитов в коротком формате. Каждый коммит отображается в одной строке с его хешем и сообщением.

**3. Почему push в чужой репозиторий не проходит?**

Если я клонирую публичный репозиторий, я могу просматривать его и изменять файлы на своём компьютере. Но я не могу отправлять изменения напрямую в оригинальный репозиторий без прав на запись (Write Permission).

Вход в GitHub подтверждает мою личность (Authentication), но не даёт разрешения изменять чужой репозиторий (Authorization).

Чтобы предложить свои изменения авторам, нужно:
1. Сделать Fork оригинального репозитория.
2. Отправить изменения в свой Fork с помощью `git push`.
3. Создать Pull Request (PR), чтобы предложить авторам принять мои изменения.

## Git 13 — Ветки (Branches)

**1. Зачем нужны ветки?**

Ветки нужны для независимой разработки новых функций, исправления ошибок и тестирования изменений без вмешательства в основную версию проекта.

Например, можно создать ветку feature1 для разработки новой функции, а основную ветку main оставить без изменений.
